# 从需求出发复习前三讲

一项需求写进模型后，至少要能回答两个问题：哪个状态会违反它，哪个事件最有可能把系统带到那个状态？下面用三个案例把这两个问题串起来。页码分别按第一讲幻灯片序号和两份 PDF 含封面的页序计算。

## 第一层　把自然语言变成可检查的性质

| 回看位置 | 先找一个坏状态 | 再选择能排除它的建模元素 |
|---|---|---|
| 银行账户，第一讲第 36–54 页 | 一个已登记的账户没有余额记录，或者余额超过上限 | 用全函数把已开户账号与余额一一对应到一个值；开户、取款等事件同步更新相关变量 |
| 查找，第一讲第 55–61 页 | 具体机报出的下标越界，或该处元素不是目标值 | 上下文约束序列和目标；游标不变式描述已扫描前缀；命中事件提供抽象下标的见证 |
| 单车道桥，第二讲第 91–163 页 | 桥上同时存在往岛和往大陆的车辆 | 计数分成三个位置，用 a = 0 ∨ c = 0 表达方向互斥，在进桥事件检查反向桥面已清空 |
| 机械压力机，第三讲第 221–233 页 | 防护门仍开着，离合器已经接合 | 分开指令和反馈，用离合器、门和电机之间的不变式约束发命令的时机 |

**自己检查。** 写下“桥上只能有一辆车”和“桥上同时只允许一个行车方向”各自的公式。前者可写为 a+c≤1，后者可写为 a=0 ∨ c=0。状态 (a,c)=(2,0) 只满足后者。选择公式前先判断课件是否允许同向多车，这个小例子足以区分两条需求。

## 第二层　判断该加哪种元素

| 你想表达的内容 | 放在哪里 | 对照工程 |
|---|---|---|
| 所有运行共同采用的容量、账号集合、设备枚举 | Context 的 Sets、Constants、Axioms | C0_Capacity，c0，MotorCtx |
| 某时刻可能发生变化的余额、游标、灯或按钮 | Machine 的 Variables；Invariants 给类型和约束 | m0，m_1a，M2_Lights，Press1 |
| 一次事件才选定的账号或下标 | Event 的 Parameters 与 Guards | 银行的 open、查找的抽象 search |
| 一个事件在何时允许发生 | 该 Event 的 Guards | ML_out 的 n<d，clutch_start 的反馈条件 |
| 一个事件发生时改动哪些量 | 该 Event 的 Actions，同一事件中的赋值并行 | 开户同时扩充账号集合、余额函数和持有人函数 |
| 相邻抽象层如何表示同一现场状态 | 具体机的连接不变式，必要时配事件 Witness | 桥上的 n=a+b+c；查找里的 k=j+1 |
| 新的内部步骤能否无止境地发生 | Variant、事件的 Convergence 及相关 PO | M1_Bridge 中的 2∗a+b，m_1a 中的 n−j |

## 第三层　读懂三种精化

**银行把业务动作拆开。** 记账前后只看账户余额，转账扣款像一次取款，到账像一次存款。加入转账编号和在途记录后，两次事件可以相隔多个其他事件。学习时写下扣款成功却尚未到账的具体状态，检查此时目的账户能否关闭、到账时谁负责检查余额上限。课件中的 FUN-5 另在教学工程的 m2 演示。

**桥梁把观察尺度变细。** M0 只看到总数，M1 看到车辆位置，M2 加两端信号灯，M3 分开传感器、现场车数和软件车数。给定一个具体事件，先问它投影回父机时是否有可观察效果，再检查应该选择父事件还是引入新的内部事件。软件暂时少记一辆车时，正在等待处理的消息也属于需要解释的状态。

**压力机逐步收紧允许的交互。** 从“发命令—收反馈”开始，依次添加按钮、离合器和门。后面的联锁层会阻止以前能做、现在有危险的事件。用同一段事件历史分别在较弱与较强的机器中走，看第一处被禁用的事件，就能定位新增需求。多数层保留设备变量，其精化重点在守卫强化与动作的模拟。

## 第四层　用最小反例准备答辩

1. **把进桥守卫 n<d 改为 n≤d 会怎样？** 在 d=n=1 时再进一辆，得到 n=2，容量不变式失败。语法和类型可以完全正确。
2. **车已经驶离传感器，为什么真实车数能先变化？** 现场事件改变真实数量并留下消息，控制器随后消费消息再更新逻辑数量。在两个时刻之间，连接不变式用待处理消息解释差值。
3. **为什么顺序查找需要保存已扫描前缀的信息？** 游标位置只说明走到了哪里。要说明输出的是第一个匹配，还需要证明之前的每个位置都不匹配。命中守卫与见证再把当前下标连到抽象选择。
4. **一个按钮为什么有电平和记忆两项变量？** 电平只告诉控制器当前是否按下。记忆记录这次按下是否已处理，避免长按导致同一请求反复触发。
5. **为什么还要构造轨迹，即使不变式都能证明？** 把所有正常事件守卫设为假，也能使许多保持义务成立。检查一条完整往返或加工周期，再写无死锁或进展条件，才能发现“安全却什么也做不了”的建模错误。
6. **无死锁能否推出每辆车最终通过？** 无死锁只要求当前至少有一种事件可以发生。某辆车可能一直得不到调度。若要保证每个等待者最终被服务，需要能区分等待者的状态、相应的时序性质和调度假设。

## 交作业时怎样讲一个模型

先说清系统边界与一条需求，用一个会违反它的具体状态说明这条需求的含义。打开上下文和机器，各指出一条环境假设与一条机器不变式。选一个关键事件，在纸上画出旧状态和新状态，解释每个守卫为何必要。最后选一项 INV、GRD、SIM 或 VAR，读出假设与目标，再用软件里的证明状态回答“这一步已经验证到什么程度”。
